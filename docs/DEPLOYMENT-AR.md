# رفع نسخة الرحمة على Vercel وRailway

الفرونت والباكند مستودعان منفصلان. استخدم الفرع `release/2026-11-07` من المستودعين معًا، وبعد نجاح فحوصات GitHub. ملفات الأسرار المحلية وحسابات الاختبار ليست جزءًا من النسخة المرفوعة.

## 1. إنشاء الخدمات

1. سجّل الدخول إلى Railway بواسطة GitHub وأنشئ مشروعًا جديدًا.
2. أضف PostgreSQL وسمِّ الخدمة `Postgres` حتى تطابق مراجع المتغيرات في القالب. تأكد من وجود قرص دائم للقاعدة.
3. أضف خدمة من مستودع `raha-medical/backend`، واختر فرع الإصدار ومجلد المستودع الجذري. توجد ملفات Docker وRailway جاهزة فيه.
4. في Vercel استورد `raha-medical/frontend`، واختر Next.js وفرع الإصدار والمجلد الجذري. أوامر التثبيت والبناء مضبوطة في `vercel.json`.
5. دوّن رابط الفرونت ورابط Railway العام للـ API. استخدم روابط HTTPS العامة، وليس localhost أو IP الجهاز.

## 2. قاعدة البيانات

قبل تشغيل API، تحتاج القاعدة الجديدة إلى الجداول. ملف `database/schema_v5.sql` في الباكند هو المخطط الكامل الحالي.

**هذا الملف يحذف مخطط public: يُستخدم فقط على قاعدة جديدة وفارغة.** لا تشغّله على قاعدة فيها بيانات. للتحديث من قاعدة سابقة توجد migrations منفصلة، وآخرها `031_prescription_text.sql`؛ حدّد الترحيلات الناقصة وخذ نسخة احتياطية قبل تطبيقها. الحاوية لا تحذف أو تعيد تهيئة الجداول تلقائيًا.

نقل بيانات النسخة المحلية قرار منفصل: لا تستورد مرضى وحسابات اختبارات السموك إلى قاعدة الاستخدام الحقيقي.

## 3. متغيرات الباكند

من Railway افتح Variables لخدمة API، ثم RAW Editor وانسخ قالب الباكند `deploy/railway.env.example`. استبدل جميع القيم التوضيحية:

- اتصال PostgreSQL يستخدم مراجع خدمة `Postgres`؛ لا تنسخه إلى الفرونت.
- `Jwt__SigningKey`: سر عشوائي ثابت، 32 حرفًا على الأقل.
- `Bootstrap__AdminPassword`: كلمة سر قوية وفريدة للمدير الأول. غيّرها عند أول دخول ثم أزل قيمة bootstrap من إعدادات الخدمة.
- `Cors__Origins__0`: رابط الفرونت فقط، مثل `https://alrahma.example`، دون مسار أو شرطة أخيرة.
- روابط الدفع والإيصالات: دومين الفرونت الفعلي كما في القالب.
- احتفظ بمفتاح توقيع الإيصالات ثابتًا: إما secret باسم `Drawer__PrivateKeyPem` أو volume قابل للكتابة عند `/data` كما يشرح دليل الباكند.

اترك البيئة `Production`؛ لا تستخدم Development لتجاوز الحماية. يبدأ Docker على منفذ `PORT` الذي توفره Railway. فحص `/health` يجب أن يعيد 200 قبل الانتقال للفرونت. شغّل نسخة API واحدة حاليًا.

## 4. متغيرات الفرونت

في Vercel > Project Settings > Environment Variables، استخدم قالب `deploy/vercel.env.example`:

| المتغير | القيمة |
| --- | --- |
| `NEXT_PUBLIC_API_URL` | `/api/v1` |
| `API_PROXY_TARGET` | رابط API على Railway دون `/api/v1` |
| `NEXT_PUBLIC_HUB_URL` | رابط API متبوعًا بـ `/hubs/live` |
| `NEXT_PUBLIC_PATIENT_APP_URL` | رابط الفرونت متبوعًا بـ `/patient` |
| `NEXT_PUBLIC_AGENT_MODE` | `simulate` للطباعة من المتصفح |

أعد النشر بعد إضافة أو تغيير المتغيرات. القيم التي تبدأ بـ `NEXT_PUBLIC_` تصل إلى المتصفح؛ لا تضع فيها كلمات السر أو مفاتيح JWT أو التخزين.

## 5. الملفات والتكاملات

صور الأطباء ونتائج المختبر والأشعة تحتاج خدمة تخزين متوافقة مع S3؛ PostgreSQL لا تكفي لحفظها. اضبط `Storage__*`، وأنشئ bucket خاصًا باسم `medical` مع CORS لدومين الفرونت للرفع بالروابط الموقعة. لا تجعل الملفات الطبية عامة. يوجد شرح في دليل الباكند.

SMS/OTP والإشعارات والمساعد تستخدم المزود التجريبي الافتراضي حتى إعداد المزود الحقيقي. في Production لا يعود رمز OTP في الاستجابة ولا يُرسل SMS حقيقي بهذا الوضع. الدفع الإلكتروني التجريبي معطل في Production؛ التحصيل في الاستقبال يبقى المسار المتاح حتى ربط بوابة فعلية. النسخ الاحتياطي المحلي على Windows لا يعمل داخل حاوية Railway؛ جهّز نسخ قاعدة البيانات والملفات واختبر استرجاعها.

## 6. اختبار ما بعد الرفع

اختبر دخول المدير وتغيير كلمة السر، عزل جلسات التبويبات، صلاحيات المختبر والصيدلية، الوصفة النصية، الأسعار والفاتورة والطباعة. افتح شاشة الانتظار وامسح رمزها من هاتف فعلي، وثبّت الحضور وتحقق من تحديث الطابور وعدم تكرار الحضور. اختبر رفع وتنزيل ملف وهمي وبقاءه بعد إعادة النشر. هذه الفحوصات السحابية مستقلة عن نجاح البناء المحلي.
